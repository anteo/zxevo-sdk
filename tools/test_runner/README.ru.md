# Тестовая инфраструктура ZX Evolution

[![English](https://img.shields.io/badge/lang-en-blue.svg)](README.en.md)
[![Русский](https://img.shields.io/badge/lang-ru-green.svg)](README.ru.md)

`runner.py` запускает C- и ASM-наборы. `suites/base.py` находит кейсы и управляет прогоном.
`suites/c.py` и `suites/asm.py` подготавливают кейсы, а `compiler.py` содержит функции для z88dk.
`emulator.py` получает результаты через ZXHost, `comparison.py` сравнивает снимки и данные, а
`profiles.py` объединяет слои профилей SDK. Метаданные, эталоны и профили находятся рядом с тестами
библиотек. Образы создаёт модуль [`fixtures/images.py`](fixtures/images.py). Код для Z80 и описание
протокола лежат в [`lib/test_support`](../../lib/test_support/).

Общий набор использует одну директорию кейсов и два машинных адаптера с раздельными выходными
каталогами. [Общие тесты](../../lib/common/tests/README.ru.md)

Если C-компилятор завершится по `SIGSEGV`, раннер сохраняет диагностику в `build.sigsegv.log` или
`library-build.sigsegv.log` и повторяет сборку один раз. Обычные ошибки компиляции выводятся сразу.

## Запуск тестов

Команда `make test` из корня SDK запускает наборы BaseConf, TSConf и общего кода. Раннеру нужны
Python 3.11 или новее и ZEsarUX с ZRCP. Переменная `ZESARUX` задаёт путь к эмулятору. По умолчанию
раннер ищет его в `PATH` и стандартных каталогах установки. Переменная `ZXEVO_TEST_ROM` задаёт ROM
для профилей `ers-rom` и `ts-bios`.

```sh
make test ZESARUX=/path/to/zesarux ZXEVO_TEST_ROM=/path/to/ZXEVO.ROM
```

Для одного набора используйте `make test-baseconf`, `make test-tsconf` или `make test-common`.
Бинарники, манифесты, отчёты и снимки попадают в `tests/build/` соответствующей библиотеки. Общий
набор добавляет подкаталог для каждой конфигурации. Команда `make clean` из корня SDK удаляет
результаты сборок, тестов и кэш Python. [Тесты BaseConf](../../lib/baseconf/tests/README.ru.md) ·
[Тесты TSConf](../../lib/tsconf/README.ru.md#emulator-tests) ·
[Общие тесты](../../lib/common/tests/README.ru.md)

### Профили C и ASM

Профили задаются в `profiles.toml` как `[profiles.<имя>]`. Поле `parent` указывает родительский
профиль. `profile = "stdio+60hz"` и `profiles = ["stdio+60hz"]` задают один запуск с двумя слоями.
Каждый элемент массива `profiles` добавляет отдельный запуск. Раннер разбирает слои слева направо и
применяет каждый один раз, начиная с его родителей. Параметр `--profile` принимает полное имя
запуска.

Метод `merge_profile` сливает упорядоченные настройки. Оба сьюта наследуют поля
`[profiles.<имя>.layout]` по отдельности, включая `code_org`, `stack_org` и `code_page`. В ASM
`code_org` должен совпадать с адресом, по которому собран бинарник. C-сьют объединяет параметры
сборки и сообщает о конфликтующих присваиваниях. C-профили SDK наследуются от `default`. Если кейс
опускает оба поля, запускается `default`. Для ASM профиль нужно указать явно. Поле `machine` в
выбранном или родительском профиле задаёт машину ZEsarUX. Все явно заданные значения `machine` в
одном запуске должны совпадать. Записи в порты добавляются по порядку, включая повторы, а
последующие слои могут переопределять настройки маппера.

Задайте `boot_pc` в профиле, чтобы раннер остановил ROM по адресу Z80 перед загрузкой кейса. При
заданном `boot_pc` параметр `boot_cycles` задаёт верхний предел числа итераций команды ZRCP `run`.
Если ROM не дошёл до нужного адреса, прогон завершается ошибкой. Профили без `boot_pc` используют
фиксированный прогон при старте.

Раннер ищет эталоны сначала в общем каталоге кейса, затем в каталогах слоёв в порядке слияния.
Последним он проверяет каталог полного имени запуска. Для `stdio+60hz` приоритет одноимённых файлов
растёт от `default/` к `stdio/`, затем к `60hz/` и `stdio+60hz/`.

### Профили и эталоны C-кейсов

Общие эталоны лежат в `cases/<путь-кейса>/`, где `<путь-кейса>` — путь к исходнику без `.c`.
Отличающиеся и дополнительные файлы лежат в `cases/<путь-кейса>/<профиль>/`. Результат, ожидаемый
только в некоторых запусках, кладите в каталоги этих профилей. Сборка и результаты каждого запуска
лежат в `tests/build/<путь-кейса>/<профиль>/`. В наборах BaseConf и TSConf `--update` обновляет
общие эталоны из первого объявленного профиля, если для файла ещё нет переопределения. Отличия
сохраняются в каталоге текущего запуска. Переопределения, совпавшие с унаследованным эталоном,
удаляются. Общий набор добавляет имя машины перед профилем в дереве эталонов и перед путём кейса в
дереве сборки. Его `--update` пишет переопределения для конкретной машины.

## Добавление набора

Новый C-набор хранит кейсы и соответствующие TOML в `tests/cases/`, а `profiles.toml` в `tests/`.
Передайте `CTestSuite` путь к тестам и имя машины ZEsarUX. Адаптер реализует следующие методы.
[Набор BaseConf](suites/baseconf.py)

- `build_target` собирает целевую библиотеку и возвращает флаги, окружение, дополнительные исходники
  и файлы, по которым определяется актуальность сборки. Укажите CRT, раскладку и входные файлы,
  влияющие на бинарник.
- `page_write` кодирует физическую страницу для окна CPU как пару из порта и значения.
- `launch_ports` настраивает начальное отображение страниц, включая резидентную W1 и ROM в W0, если
  он нужен. Эти записи выполняются перед отображением и загрузкой блоков манифеста.

Почтовый ящик, лог и инициализированные данные находятся в W1. Эта страница и область передаваемых
данных должны оставаться доступны, пока хост читает результат. Профиль задаёт адреса кода, DATA, BSS
и стека. Раннер может разделить программу между W0 и W1 или разместить код целиком в другом окне.
Вариант с отдельным окном позволяет оставить ROM в W0 для тестов его API.

На Z80 подключите `zx_test.h` и вызовите `zx_test_init()` до аппаратной настройки. Для проверок и
результатов используйте `ZX_ASSERT` и `zx_test_step_*`. Завершайте кейс через `zx_test_finish()`. На
старте маскируемые прерывания отключены. Кейс может включить их после подготовки векторов.

В TSConf `emulator_steps` может содержать `tsconf_registers` с ожидаемыми значениями `xxAF`. Ключи —
шестнадцатеричные индексы регистров, значения — байты. Хост сверяет их на паузе. Поле `joystick`
задаёт байт ввода перед следующим шагом.

### Образы для эмулятора

Опишите нужные C-кейсу устройства в его TOML. Раннер создаёт каждый образ в каталоге запуска
`build/.../<профиль>/emulator_images/` и подключает его к ZEsarUX без сохранения записей на диск.
Пути к образам в `manifest.json` отсчитываются от каталога самого манифеста.

```toml
[emulator_images.ide]
fixture = "ers-fat32"
filename = "hdd.img"
size_sectors = 131_072
mount_list = ["E:/DOCS/DISK.TRD C:"]
```

Ключи устройств — `mmc` для SD, `ide` для HDD и `trd` для образа Beta Disk. `ers-fat16` содержит
файлы для тестов SD в ERS, `ers-fat32` — файлы для тестов HDD в ERS, а `ts-fat32` —
фрагментированный файл и вложенный каталог для тестов TS-FAT. Для FAT `size_sectors` задаёт размер
всего образа в секторах по 512 байт. Необязательный `mount_list` записывает указанные строки в
`IMAGE.MNT` на `ers-fat32`. У образа `trd` фиксированный размер 640 КиБ. Для него достаточно указать
имя файла.

## ZXHost на целевой машине

ZXHost — небольшой C-модуль для программы на ZX. Он публикует в памяти почтовый ящик с запросом и
результатом и лог фиксированного размера. Адреса, поля, версия и состояния заданы в
[`protocol.json`](../../lib/test_support/protocol.json). Перед линковкой сгенерируйте константы C.

```sh
python3 tools/test_runner/zx_host/generate_header.py \
  lib/test_support/protocol.json build/zx_host_config.h
```

Добавьте `lib/test_support/c` и каталог сгенерированного заголовка в пути поиска, затем слинкуйте
`lib/test_support/c/zx_host.c`. Вызовите `zx_host_init()` перед чтением `zx_host_get_request()`.
Инициализация сохраняет команду, аргументы, номер запроса и флаг отмены, записанные хостом. При
новом запросе код Python сбрасывает флаг отмены.

Программа может проверять `zx_host_cancelled()`, записывать результат через `zx_host_set_results()`,
дополнять лог через `zx_host_log_text()` и завершать обработку со статусом `ZX_HOST_DONE`,
`ZX_HOST_ABORTED` или `ZX_HOST_ERROR`. Значения команд и аргументов определяет программа. Хост
записывает номер запроса последним, целевой код сохраняет его в ответе.

Тест может объявить номер и имя шага перед выполнением. Для этого он выставляет `BEGIN` (бит 3) и
`MORE` (бит 1) в `result2` и ждёт следующего номера запроса. Результат шага содержит тот же номер,
флаги вывода и диагностику. Имя уже есть у раннера. Однофазный шаг отправляет имя вместе с
результатом. При завершении всего теста флаг `MORE` сбрасывается.

В C вызовите `zx_test_step_begin("name")` перед началом работы, а при выдаче результата передайте
`NULL` вместо имени, например в `zx_test_step_marker(NULL)`.

### Тесты на sjasmplus

Для ASM сгенерируйте `zx_host_config.inc` из того же `protocol.json`, передав генератору
`--format sjasmplus`. Подключите `zx_test.inc` до кода и включите `zx_host.asm` и `zx_test.asm` из
`lib/test_support/z80/` в собираемый бинарник. После `CALL zx_test_init` объявляйте начало через
`ZX_TEST_BEGIN "name"`. Завершайте шаг через `ZX_TEST_MARKER` для шага без данных, `ZX_TEST_SHOT`
для снимка и `ZX_TEST_DATA address, length, kind` для данных. `kind` выбирает hex-дамп (`0`), текст
(`1`), бинарный файл (`2`) или TOML (`3`). Перед переходом в `zx_test_finish` передайте статус в A и
указатель на строку лога в HL. Для завершения без сообщения передайте `HL=0`.

Для именованных числовых результатов вызовите `zx_test_output_begin`, добавьте поля через
`ZX_TEST_FIELD "carry", (result_carry)` или `ZX_TEST_FIELD16 "sp", (result_sp)`, затем опубликуйте
результат через `ZX_TEST_TOML`. Раннер сравнит поля с эталоном `.toml`. C-кейсы могут опубликовать
такой же результат через `zx_test_step_toml()`.

Команда `python3 tools/test_runner/runner.py asm check --suite-dir … --build-dir … --rom …` собирает
и запускает выбранные кейсы. `asm build` с теми же параметрами собирает кейсы и готовит манифесты
без запуска эмулятора. По умолчанию раннер использует `sjasmplus` из `PATH`. Параметр `--sjasmplus`
задаёт исполняемый файл, а `--include-dir` добавляет путь поиска include-файлов. Шаг `BUILD`
сохраняет вывод ассемблера в `<build-dir>/<кейс>/<профиль>/build.log`. Профили запуска задаются в
`profiles.toml`. В `cases/<кейс>/main.toml` рядом с `main.asm` укажите `profile = "tsconf-bios"` для
одного запуска или `profiles = ["tsconf-bios", "tsconf-basic48"]` для нескольких. ASM-кейс может
объединять профили через `+` по тем же правилам, что и C-кейс.

Имена эталонов имеют вид `<кейс>.<NN>_<тег>.<ext>`. Общие файлы лежат рядом с `main.toml`, а
переопределения — в каталогах с именами профилей. Эта же команда принимает `baseconf`, `tsconf` или
`common` для C-наборов SDK.

ASM-кейс может подменить код в своей копии ROM. В `main.toml` задайте `[rom_patch]` с полями `bank`,
`symbol` и `source`. Раннер собирает исходник, путь к которому указан относительно `main.toml`. Для
готового бинарника можно указать `file` относительно `<build-dir>/<кейс>/`. Таблица символов ROM
передаётся через `--rom-symbols`.

### Модули Python

- `tools/test_runner/zx_host/protocol.py` проверяет и кодирует поля почтового ящика.
- `tools/test_runner/zx_host/manifest.py` описывает параметры запуска, блоки и группы тестов,
  сериализует манифест в JSON.
- `tools/test_runner/zx_host/basic.py` формирует BASIC-команды `POKE` для начального запроса.
- `tools/test_runner/zx_host/session.py` предоставляет `ZXHostSession`. Он загружает блоки
  манифеста, отправляет команду, ждёт ответ с нужным номером и поддерживает запрос отмены.
- `tools/zesarux/runner.py` запускает ZEsarUX и предоставляет клиент ZRCP.

Если программа переносит почтовый ящик после запуска, манифест может описать перенос через
`runtime_memory`. Сессия проверяет, что ящик и лог укладываются в указанное окно CPU и диапазон
копирования.

```python
from tools.test_runner.zx_host import ZXHostSession

with ZXHostSession("build/manifest.json", "/path/to/zesarux") as session:
    session.start(command=1, args=(0, 0))
    result = session.wait_for_completion(timeout=15)
```

`start()` подготавливает запрос и оставляет CPU в пошаговом режиме. Между запусками CPU хост может
передать нажатия клавиш или вызвать `request_cancel()`. Закрывайте сессию через контекстный менеджер
или `close()`. `detach()` оставляет эмулятор запущенным.
